# Page notes — the reasoning behind individual pages

Split out of `CLAUDE.md` on 2026-09-28. That file keeps one short row per task
(where to edit, what not to break); the full history of why each page is
shaped the way it is lives here, verbatim. Read the section for a page before
changing it.

## Compliance board

*Task:* Change the league-wide compliance board

The **Compliance tab** of `committees/rosters/index.html` — the first of four tabs, public and read-only. Its script is its own IIFE at the bottom of that file, separate from the reconciliation script above it, and its DOM ids are all `comp-`-prefixed so nothing collides. Rules: **`cap-health.js`**, the same module as the row above; data: `GET /api/cap-history/current` (`nbn-api/routers/cap_history.py`), which already returns that module's exact inputs for all 30 teams. **The page does no cap math and states no rule of its own** — it calls `CapHealth.standing()` once per team and arranges the answers, so a condition added to `cap-health.js` appears here without an edit. It can price a § 2.1a Empty Roster Charge since 2026-09-19, but still doesn't compute one — `cap_history.build_rows` folds the charge into both salary figures and reports it as `empty_roster_charge`, and the page passes that straight into `standing()`. Don't recompute it here from the roster count; `computeEmptyRosterCharge` in `teams/team.js` is the other implementation and it is unreachable (that file injects a page on load). `standing()` still supports being called without `erc` and names the floor instead, which is what a cap-history row written before that date gets. Covered by `tests/frontend/run.js`

## Rosters committee

*Task:* Change the rosters committee dashboard, or the cap-sheet / picks / data-quality reconciliation

`committees/rosters/index.html` — four tabs. **Compliance** is our own data against the rulebook (row above). The other three are our data against the league's cached spreadsheet, from `/data/poopoo.json` written by `build/poopoo.py`; a diff there is bookkeeping to settle, not a team in breach, and the page says so. To hand a pick to the committee with what's known so far, add it to `pick-committee-notes.json` in NBS_DATA_DIR (keyed `"YEAR|ROUND|ORIG"`, `{added, title, text}`). The next `poopoo` run pins it to that pick's card under **Committee tasks** at the top of the Picks tab, where it stays until the entry is deleted. Superseded `/poopoo` and `/compliance`, both deleted 2026-09-19 with no redirect stub (`/poopoo` was admin-only in nav; `/compliance` is reachable at the new path). `setupTabs()` runs **before** the poopoo fetch, not after it — with Compliance as a tab, a missing `poopoo.json` would otherwise return early and leave every tab button dead, including the one tab that doesn't need that file

## Stats committee

*Task:* Change the stats committee dashboard (the day-by-day box score worklist, screenshot upload, the day's VOD link, build health)

`committees/stats/index.html` — one self-contained file, public. The worklist is one card per day, one row per game, one box per team side: the `stats` role pastes/drops a screenshot into a side (`POST /api/boxscore/upload/side`), and a game reads Needs screenshots → Needs TEAM → Ready to parse → Entered. Screenshot storage, the 14-day keep after commit and the public list are `nbn-api/routers/boxscore_shots.py`. Also reads `GET /api/build/status`, `GET /api/schedule`, `GET /api/boxscores/games`, `GET /api/boxscore/screenshots`, `GET /api/streaming-days`. A scheduled game is matched to a box score on **date plus its two teams unordered**, so a game entered with the sides swapped doesn't read as missing. Deliberately **not** in `tests/frontend/run.js`: its one countable list is empty in the offseason and empty again whenever the committee is caught up

## Roster Settings

*Task:* Change the Roster Settings section (jersey #, secondary position, player minutes)

`setupTeamSettingsTab` — `teams/team.js`. Folded into the Coaching tab (`#tab-coaching`) 2026-09-04, then merged 2026-09-04 with the Player Minutes depth chart that used to live in Coaching Profile below it — both are player-indexed tables ("list every roster player, edit something about them"), so they're now one table, one row per player, rather than two. **A slot is which row a player is in, not a field they pick** (changed 2026-09-04 from a per-row `<select>` of all 15 slots to this): table order *is* the depth chart, row 0 always `CS.MINUTES_SLOTS[0]` (`PG`), row 1 `SG`, … row 4 `C`, row 5 the 6th man, … row 14 the 15th man, and reordering is drag-and-drop (a `⠿` handle column, edit mode only). Not native HTML5 DnD — no touch equivalent on iOS Safari — and not Pointer Events either, which still let a real phone's page-scroll win over the drag (`touch-action: none` + `setPointerCapture` weren't enough; a captured pointer's `touchmove` can still be browser-treated as passive, silently no-opping `preventDefault()`). What actually works: raw `mousedown`/`touchstart` on the handle to start, `document`-level `mousemove`/`touchmove`/`mouseup`/`touchend`/`touchcancel` while live, with `touchmove` registered `{ passive: false }` specifically so `preventDefault()` takes effect. `orderedRows()` opens Edit with the roster already arranged in last-saved slot order (whoever's `minutes[slot].slug` matches first, in slot order, then anyone unassigned after) rather than raw roster order. Nothing is kept in sync as rows move — `minutesFromDom()` derives the whole slot-indexed `minutes` object fresh from live DOM order (row index → `CS.MINUTES_SLOTS[i]`) whenever it's needed (the running total, and the final save), which is also what makes a slot holding at most one player automatic (one DOM position, one row) instead of the exclusivity bookkeeping the old per-row dropdown needed. An **Auto-sort by OVR** button (edit mode, next to Save/Cancel) reorders the table via the same `computeStartingFive` (`teams/lineup.js`) the Rosters tab's Depth mode already uses for its starting five — best eligible player per position, without stranding a slot a dual-eligible player was needed elsewhere for — then ranks everyone left over by OVR into the bench slots. It's a starting arrangement to drag from, not a save by itself; a player's already-entered minutes/RES travel with their row since auto-sort only moves rows, never rebuilds them. The stored shape itself is unchanged — still slot-indexed, in the *coaching-settings* record, not the player bio — since `committees/stream/index.html`'s streamer dashboard reads that same shape directly and unmerged (`CS.renderReadOnly`'s own Player Minutes card, `opts.skipMinutesCard` left false there). Saving jersey/secondary-pos goes to `PUT /api/players/{slug}/team-settings` per changed player as before; saving minutes goes to `PUT /api/coaching-settings/{team}` — a full-replace-both-fields endpoint — so a minutes-only save always resends the team's current (unedited) `values` alongside the edited `minutes`, and a jersey-only save skips that request entirely (a `minutesDirty` flag decides), since PUTting there unconditionally sets `pending: true` and would falsely tell the streamer something coaching-related needs re-entering

## Calendar

*Task:* Change the calendar page (public, read-only game list + fixture/vesting events)

`calendar/index.html` — one self-contained file; game data from `GET /api/schedule` merged with `GET /api/calendar/games`, keyed by date into `scheduledGamesByDate` (`nbn-api/routers/schedule.py` / the calendar-games endpoint). `addMonthCell`'s `.schd-pip` is where an upcoming fixture renders, and where who's claimed it (`streamer`) and whether it's flagged as one (`stream`) show — both public data, read-only here. A date's `.yt-pip` (▶️ VOD) is separate — one per day, not per game, from `GET /api/streaming-days` (`nbn-api/routers/streaming_days.py`), attached inline on `/committees/stream`'s Claim Games day dividers. `/schedule` is retired to a redirect stub pointing here (Discord links still point at it); claiming/flagging/marking days done is `/committees/stream`, the streamer role's own page, not this one

## Streamer dashboard

*Task:* Change the streamer dashboard (My games, game claims, the stream flag, the day mark-done control, or the Coaching Settings entry queue)

`committees/stream/index.html` — one self-contained file, gated to the `streamer` role (and `admin`) at the page level; three tabs. **My games** (the default, `renderMine`) is the game-day view: the streamer's claimed days, each game's two teams with coaching status and View / Mark entered inline, the day's Mark done, and a warning listing the next 7 days' unclaimed games with a Claim day button. It renders the same state as the other two tabs, so an action in any tab re-renders it. Since 2026-09-24 the day's VOD link is set on `/committees/stats` (the API takes `stats` or `streamer`); this page only shows it. "Claim Games" is the same season browser as `/schedule`, moved here because claiming/flagging are the only writes it makes: a streamer claim (`streamer`, who's broadcasting) and the stream flag (`stream`, whether the game itself is marked as one) — two independent fields, neither implies the other. Its day-divider rows (`dayRowEl`) also carry that date's slate controls (`daySlateControls`) — mark-done (`nbn-api/routers/streaming_days.py`, one shared flag per date, not per streamer; shown on today and past dates only), Claim day, and a ▶️ link to the VOD when Stats has set one (it's what shows up as `/calendar`'s `.yt-pip` above). Mark-done is open to any `streamer`/`admin` regardless of who (if anyone) claimed a game that night. Marking a day done, saving coaching settings and entering them each send an inbox message — `nbn-api/routers/game_day_notify.py`. "Coaching Settings" is the entry-queue dashboard for the row below — sorted by each team's soonest next game (`nextGameFor`), not just pending/entered status

## Coaching settings

*Task:* Change the coaching-settings field/option schema, or the Coaching tab on team pages (which also holds the Roster Settings section — see above)

**`coaching-config.js`** at the repo root — one schema (points of emphasis, coach style/playbook, coaching sliders, the two point-buy pools, the player-minutes depth chart), shared by `setupCoachingSettingsTab`/`setupTeamSettingsTab` (`teams/team.js`) and `committees/stream/index.html`'s Coaching Settings tab, so a team's saved settings render identically everywhere. `renderReadOnly(container, record, opts)`'s `opts.skipMinutesCard` exists solely so `setupTeamSettingsTab` can render minutes itself, merged into its per-player table, without `setupCoachingSettingsTab`'s own read view (which calls the same function) showing the same minutes twice on one team page — default false, so `/committees/stream`, which has no such table, is unaffected. The server (`nbn-api/routers/coaching_settings.py` — `GET`/`PUT /api/coaching-settings/{team}`, `POST .../enter`) is deliberately schema-blind and stores whatever blob is sent, since the field list is 2K-version-coupled and expected to change yearly — a new season's fields are a `coaching-config.js`-only edit, no backend change. Saving is never blocked on an unbalanced point-buy pool or the minutes grid; `CoachingSettings.validityIssues()` is the one place "unbalanced" is computed, and it's what flags an inconsistent save to both the team that entered it and the streamer about to act on it

## Power rankings

*Task:* Change power rankings — the ballot, the consensus math, blurbs

Rules: `nbn-api/routers/news_rankings.py` (pure — no FastAPI, no I/O, so it is directly testable and is what `tests/test_news_rankings.py` pins). Routes: the `_mutate_ranking` block in `nbn-api/routers/news.py`. Workspace UI: `news/rankings/rankings.js`; published table: `renderRankings` in `news/view/index.html`. A power-rankings article is an ordinary news article with a ballot phase between draft and publish. Once published it is a **multi-author piece**: the byline (article page, news cards, homepage feed, Discord embed, link card) is everyone `_credited` in `nbn-api/routers/news.py` returns — the author, every member who submitted a ballot, and every member whose blurb is printed. Only the author (and editors) can still edit it. **Blurbs open at `voting`, not at the close of it** (`BLURB_PHASES` in `news_rankings.py`, mirrored in `rankings.js`), so a voter claims and writes while the ballot is still out; during that phase the claim board is its own alphabetical list under the ballot (`renderBlurbBoard`), never ordered by the standing, since the standing is the thing a voter must not see mid-vote. Unlike ballots, blurbs are **not** blind while voting runs — league decision, 2026-08-30 — **the order is the plain average of the ballots and the author cannot reorder it**, so don't add an override without the league deciding to. Teams level on the average **share a rank** (T-13, T-13, 15) — nothing hidden breaks a tie. An edition with no `prev_id` can still show ▲▼ against a `baseline` (`{label, ranks}`, set by `PUT /api/news/{id}/rankings/baseline`), which is how the imported February 2026 sheet moves against January. Each `final` row also carries a frozen `roster` (the team's whole active roster by OVR, stamped by `_team_roster_snapshot` in `publish_article` at publish time) and `season_line` (its last completed season out of `standings-history.csv`) — like the rest of `final`, these are captured once and never reconstructed, so a later trade or rating change can't rewrite what an already-published edition showed. A collapsed row is rank, movement, team, every voter's placement (the best and worst ballot marked green/red, unexplained and deliberately so, which is what the row used to spell out as `high 2 · low 5`; a unanimous team has no spread and nothing is marked) and two clamped lines of its blurb; clicking it expands a panel that leads with the full blurb and its byline, then the season's KPI tiles, the projected starting five via `computeStartingFive`, and the rest of the roster numbered on from 6 — the five are not repeated in the list, and the list runs to the end of the roster rather than to a cap, so it needs no heading admitting what it hides. Those numbers are depth order, not OVR rank: a centre rated 7th can start ahead of a guard rated 5th. A row is expandable if it has **any** of those three — the February edition froze no roster but has blurbs, and gating on the roster alone would have put them out of reach. The **whole** roster is frozen even though only 8 are shown, because the starting five is computed from all of it — the only centre on a team can sit well outside the top 8 — and because the panel is a claim about the team the ranking was *voted on*. An unpublished ballot preview has no `final` yet, so `renderRankings` live-fetches via `loadTeamSnapshots` there instead; an edition published before these fields existed (the imported February 2026 sheet) renders as plain rows with nothing to expand

## Owners page — data flow and `COLS`

1. `fetch('/data/owner_stats.csv')` → `parseCSV(text)` → array of row objects keyed by CSV header
2. `buildTable(rows)` creates the `<table>`, renders `<thead>` from the `COLS` array, attaches sort click handlers, calls `rebuildBody`
3. `rebuildBody(rows, tbody)` sorts rows and re-renders all `<td>` cells on every sort change

### COLS array (owners/index.html)

Each entry in `COLS` (`owners/index.html`) defines a column:
- `key` — CSV field name (used as fallback cell text)
- `sortField` — the CSV field actually sorted on (may differ from `key`)
- `cls` — space-separated CSS classes applied to both `<th>` and `<td>`
- `display(row)` — optional function returning the cell's display string; omit to use `row[key]` directly
- `defaultDir` — sort direction when first clicking this column (`-1` = descending, `1` = ascending)

The `buildTable` function in `teams/team.js` uses the same shape for team-page tables.

## Special cell rendering

Custom rendering is done inside `COLS.forEach` / `renderCell` callbacks. The `championships` column in `owners/index.html` is the canonical example: it creates a `.trophy.trophy-gold` `<span>` instead of plain text. In `teams/team.js`, `makeSeasonRenderCell` handles FOTY/COTY badges and playoff result coloring.

RTG/DIFF columns get heat-map coloring via inline `td.style` (hue 0–120 mapped to min–max of the column).

## NBNTV Classics blurbs

`nbntv-classics/index.html` stores blurbs as a plain JS object (`BLURBS`) keyed by `"{DATE}_{player-slug}"` (e.g. `"2021-06-20_curry-stephen"`). This key is stable across rank changes. Empty string means the blurb hasn't been written yet.

## Team page edit mode

The "Edit" button on Roster and Draft Picks sections in team pages calls `setupEditable`, which uses `buildEditableGrid` for in-browser table editing. Saves go to the API backend (`PUT /api/roster/{ABB}`, and `PUT`/`DELETE /api/picks/{year}/{rnd}/{orig}` one pick at a time) with a `Bearer` token. Token is prompted via a modal and persisted in `localStorage`. A 403 response clears the stored token.
